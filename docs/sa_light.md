# Static Analysis Light в CI (CODESYS 3.5.17.30)

Как включить правила Static Analysis Light скриптом, почему находок нет в `cds.py build` и как
`ci/sa_check.py` и `ci/sa_report.py` превращают коды `SAxxxx` в отчёт с политикой базовой линии.
Всё ниже, кроме отмеченного, проверено прогонами на CODESYS V3.5 SP17 Patch 3 (3.5.17.30, 32 бит,
сборка ОВЕН, русская IDE) 16.10.2026; зонды — намеренно плохой ST
([ci/tests/samples/sa_probe_src/](../ci/tests/samples/sa_probe_src/)).

## Коротко

| Вопрос | Ответ | Чем проверено |
|---|---|---|
| Какие правила есть в Light | шесть: SA0004, SA0006, SA0027, SA0028, SA0033, SA0167 (таблица ниже) | перечисление `RuleId` плагина `StaticAnalysisManager.plugin` 3.5.17.20 (отражение .NET) и находки зонда по всем шести |
| Что включено по умолчанию | ничего: в проекте, созданном `cds.py import`, все правила выключены | зонд с нарушениями всех шести правил: «Доп. проверки кода завершены -- 0 ошибки (-ок)» |
| Штатный API Scripting | нет: `ScriptProject.project_settings` (`ScriptProjectSettings`, с 3.5.12.10) умеет только загрузку исходников (`set_sourcedownload`) | стабы `ScriptLib/Stubs/scriptengine/ScriptProject.pyi` |
| Импорт файла настроек | у Light нет: загрузка и сохранение конфигурации `*.csa` — только в диалоге полной версии (Professional); `IStaticAnalysisManager.Configure(XmlDocument)` в Light создаёт элемент управления Professional — не проверялось | ресурсы и IL плагина |
| Можно ли включить скриптом | **да, через внутреннее хранилище настроек проекта** — те же ключи, что пишет диалог IDE; `ci/codesys/sa_light.py` | 13 находок зонда после записи ключей; dump ключей |
| Когда выполняются правила | **только при генерации кода** (`app.generate_code()`, в IDE — «Компиляция → Генерировать код» или вход в систему). `app.rebuild()`, который вызывает `cds.py build`, их не выполняет | rebuild с включёнными правилами — 0 находок, generate_code в том же сеансе — 13 |
| Сохраняются ли настройки скрипта | нет: `proj.save()` их не записывает (проверено дважды, в том числе с «грязным» проектом); IDE переносит их в объект «Установки проекта» отдельным вызовом | повторное открытие проекта: ключ `Rules` пуст |
| Что делают находки с загрузкой | любая находка (даже настроенная как предупреждение) добавляет в категорию компиляции служебную ошибку «Есть сообщения доп. проверок кода», итог генерации — «Компиляция завершена -- 1 ошибок, …: загрузка невозможна» | журналы `ci/tests/samples/sa_probe.log`, `sa_tests_project.json` |
| Подавление в коде | `{attribute 'analysis' := '-33'}` перед объявлением переменной или POU, `{attribute 'no-analysis'}` — объект целиком | зонд: `iUnusedLocal`, `F_SaTemp`, `FB_SaSkip` — без находок |
| Код шаблона | `src/` — 0 находок; тестовый проект (`--tests`) — 11 × SA0167: экземпляр `fbDut` в `VAR` методов-тестов (так задумано, [ASSUMPTIONS.md, C9](ASSUMPTIONS.md)) | `ci/tests/samples/sa_clean.json`, `sa_tests_project.json` |

Отсюда решение тулкита: **правила включаются только на время сеанса анализа и в проект не
сохраняются**. Проект остаётся тем же файлом (отпечаток `cds.py` не меняется), а находки SA не
ломают загрузку в `cds.py test`. Проверяется рабочий проект (`src/`); тестовый — по `--tests`.

## Правила Static Analysis Light

Названия — как в диалоге русской IDE («Проект → Установки проекта → Static Analysis Light»,
вкладка «Доп. проверки компилятора»).

| Код | Название в IDE | Что находит | Пример находки (зонд) |
|---|---|---|---|
| SA0004 | Множественный доступ по записи на выходе | выход `%Q` записывается в нескольких местах | `Множественная запись на выходе '%QX0.0'` — по строке в `PRG_Main` и `PRG_SaTask2` |
| SA0006 | Параллельный доступ | запись в одну переменную из разных задач | `Параллельный доступ по записи к 'diShared' в Задачах MainTask, SlowTask` |
| SA0027 | Многократное использование имени | имя переменной совпадает с объектом или константой перечисления | `Имя переменной 'F_Clamp' в 'FB_SaBad' уже используется для объекта в это приложение` |
| SA0028 | Перекрывающиеся области памяти | переменные `AT %M…` на общей памяти | `wOverlapA AT %MW10` и `bOverlapB AT %MB21` под заголовком «Следующие переменные обращаются к одной и той же памяти:» |
| SA0033 | Неиспользуемые переменные | объявленные и нигде не используемые переменные (POU, методы, GVL) | `Неиспользуемый Переменная 'iGlobalUnused'` |
| SA0167 | Сообщать о временных экземплярах ФБ | экземпляр ФБ в `VAR` функции или метода (создаётся при каждом вызове) | `Временный экземпляр ФБ: 'fbPulse'` |

Остальные правила (SA0001 и далее: недостижимый код, `CASE` без `ELSE`, неявные и явные
преобразования, сравнение `REAL` на равенство, пустые операторы и т. д.) — только в платном
CODESYS Static Analysis. Зонд с такими конструкциями (`RETURN` перед кодом, `CASE` без `ELSE`,
`rIn = 1.5`, пустой `;`, `DINT_TO_INT`) в Light находок не дал. Неявное сужение `DINT → INT` —
это не правило SA, а ошибка компилятора `C0032`.

Сообщения: категория «Доп. проверки кода» (GUID `220493a1-f49b-4416-9a3f-a545db707cbe`), префикс
`SA`, номер — номер правила (`build.py` шаблона пишет код `SA0033`), объект и позиция — как у
сообщений компилятора, поэтому `source_location()` шаблона даёт файл и строку раскладки
(`src/POUs/FB_SaBad/FB_SaBad.decl.st:14`, `src/GVLs/GVL_SaProbe.gvl.st:8`). Перед находками и
после них — строки «Доп. проверки кода...» и «Доп. проверки кода завершены -- N ошибки (-ок)»
(N — все находки, и ошибки, и предупреждения). Без генерации кода эти две строки тоже есть —
с N = 0.

## Как правила включаются скриптом

Внутренние имена найдены отражением .NET в процессе CODESYS (список типов плагина, константы,
дизассемблированный IL методов `OptionsHelper`, `BasicCheckNode.Save`, `StaticAnalysisManager`):

| Что | Значение |
|---|---|
| сборка | `StaticAnalysisManager.plugin`, 3.5.17.20 (`PlugIns\568ba54b-4638-4ad1-af1c-dd9209a939fd\`) |
| хранилище | `_3S.CoDeSys.StaticAnalysisManager.APEnvironment.OptionStorage` → `IOptionStorage.GetRootKey(OptionRoot.Project)` |
| ключи | `{29BD8D0C-3586-4548-BB48-497B9A01693F}\Rules\<номер правила>`: `bActive` (Boolean), `bWarning` (Boolean, по умолчанию — ошибка) |
| как пишет диалог IDE | `OptionsHelper.ClearAll()`, затем для каждого правила `CreateSubKey("<номер>")["bActive"] = <флажок>`; `bWarning` диалог Light не пишет — в IDE находка всегда ошибка |
| как читает анализ | `OptionsHelper.ReadRule`: нет ключа — значение по умолчанию (выключено) |
| когда перечитывает | изменение ключа под корнем SA вызывает `StaticAnalysisManager.Reset()` |
| когда проверяет | по IL: `OnAfterCompile` запускает участников анализа только для проекта-библиотеки; для приложения находки появляются после генерации кода (прогоны ниже) |

`ci/codesys/sa_light.py` пишет эти ключи для всех шести правил (режим `error` — `bWarning = FALSE`,
`warning` — `TRUE`, `off` — `bActive = FALSE`), сверяет режимы с тем, что видит менеджер
(`StaticAnalysisManager.Rules`), вызывает `app.generate_code()` и собирает сообщения в формате
`build.py`. Если сборки, типа или свойства нет (другая версия CODESYS), шаг завершается с кодом 3 и
сообщением со ссылкой на ручной шаг ([MANUAL_STEPS.md, раздел 16](MANUAL_STEPS.md#16-static-analysis-light-правила-в-ide)).

Почему настройки не сохраняются: диалог «Установки проекта» после сохранения всех страниц
сериализует корень `Project` хранилища (`IOptionStorage.Save(OptionRoot.Project, stream)`) в
скрытый объект проекта (`IWorkspaceObject.OptionData`) через `IObjectManager.SetObject`. Скрипт
этого не делает, а `proj.save()` настройки из хранилища не переносит. Повторить путь IDE можно,
но это ещё глубже во внутреннем API, а для CI не нужно: правила включаются каждый прогон.

## Команды

```bat
python tools/codesys/cds.py build
python ci/sa_check.py
python ci/sa_report.py
```

Первая команда собирает рабочий проект из `src/` (как обычно), вторая включает правила на время
сеанса и генерирует код (`build/sa.json`, `build/sa.log`), третья строит отчёт
(`build/sa_report.md`, `build/sa_report.json`) и завершается с кодом 1, если есть новые находки.
Команды одинаково работают в cmd, PowerShell и Git Bash; в репозитории-потребителе — путь к
`ci/` копии тулкита и `--root .` (так их вызывает `plc-codesys.yml`).

`ci/sa_check.py [--root R] [--tests] [--rules FILE] [--out FILE] [--log FILE]`:

- правила — `--rules`, иначе `<root>/ci/sa_rules.json`, иначе [ci/sa_rules.json](../ci/sa_rules.json)
  тулкита (все шесть — `warning`);
- запускает CODESYS той же строкой, что `cds.py` (функции `cdshost.cli` шаблона: `run_codesys`,
  `repo_lock`), дописывает к сообщениям `source` (`source_location` шаблона);
- предупреждает, если `src/` изменились после `import` или проект сохранён в IDE (по
  `build/codesys/state.json`);
- коды выхода: 0 — анализ выполнен (находки на код не влияют); 1 — ошибки компиляции при
  генерации кода; 2 — аргументы или файл правил; 3 — окружение или внутренний API; 4 — таймаут;
  5 — блокировка. Время — около 10 с.

`ci/sa_report.py [--root R] [--input FILE] [--baseline FILE] [--fail-on new|any|never]
[--json FILE] [--md FILE] [--summary FILE] [--annotations [--path-prefix P]] [--allow-incomplete]
[--update-baseline] [--max-rows N]`:

- вход — `build/sa.json` (по умолчанию), `build/sa.log`, а также `build/build.json` и
  `build/build.log` из `cds.py build`: формат сообщений тот же, но без генерации кода анализ
  помечается неполным;
- место находки — поле `source`; в журнале его нет — тогда `source_location` шаблона по объекту и
  позиции (вход из журнала и из JSON дают одинаковые находки — тест `test_probe_log_equals_json…`);
- `--annotations` — команды GitHub Actions `::error file=…,line=…,title=SA0033 …::…` для новых
  находок (`warning` при `--fail-on never`), `--summary "$GITHUB_STEP_SUMMARY"` — Markdown в сводку;
- коды выхода: 0 — политика выполнена; 1 — нет, или анализ неполный (не было генерации кода, SA
  не выполнялся, ошибки компиляции) — кроме `--fail-on never` и `--allow-incomplete`;
  2 — аргументы или неверная базовая линия; 3 — нет входного файла.

## Отчёт

`build/sa_report.md` — таблица параметров (вход, проект, правила, базовая линия, политика, итог),
сводка по правилам (всего, новых, в базовой линии) и по разделу на правило: место
`файл:строка`, объект, важность, сообщение (с заголовком группы для SA0028), статус — «новая» или
«базовая линия: <обоснование>». Затем — записи базовой линии без находок («исправлено — уберите
их») и замечания (нет базовой линии, неполный анализ, расхождение числа находок с итогом CODESYS).

`build/sa_report.json` (`schema: 1`):

```json
{
  "tool": "CODESYS Static Analysis Light", "input": "build/sa.json", "project": "…\\plc-demo.project",
  "rules": [{"rule": "SA0033", "mode": "warning", "name": "Неиспользуемые переменные"}],
  "analysis": {"complete": true, "sa_started": true, "code_generation": true, "compile_errors": 0,
               "reported_by_codesys": 13},
  "policy": "new", "baseline": "ci/sa_baseline.json", "passed": false, "verdict": "новых находок 13 (вне базовой линии)",
  "totals": {"findings": 13, "new": 13, "baseline": 0, "fixed": 0,
             "by_rule": {"SA0033": {"total": 3, "new": 3, "baseline": 0}}},
  "findings": [{"rule": "SA0033", "name": "Неиспользуемые переменные", "severity": "Warning",
                "message": "Неиспользуемый Переменная 'iUnused2'", "group": null, "object": "FB_SaBad",
                "position": "Строка 14 (Объявл.)", "file": "src/POUs/FB_SaBad/FB_SaBad.decl.st",
                "line": 14, "status": "new", "reason": null}],
  "fixed": [], "notes": []
}
```

## Базовая линия

[ci/sa_baseline.json](../ci/sa_baseline.json) — принятые находки с обоснованием (у `src/` этого
репозитория их нет):

```json
{"schema": 1, "findings": [
  {"rule": "SA0167", "object": "FB_Example_Test.ManualFollowsCommand",
   "file": "tests/POUs/FB_Example_Test/ManualFollowsCommand.method.decl.st",
   "message": "Временный экземпляр ФБ: 'fbDut'", "count": 1,
   "reason": "C9: новый экземпляр при каждом вызове метода-теста — так задумано"}
]}
```

- Сравнение — по правилу, объекту и тексту сообщения, **без номера строки**: сдвиг строк не делает
  находку новой; одинаковые находки считаются по `count`.
- Текст сообщения зависит от языка IDE: базовая линия, снятая в русской IDE, в английской не совпадёт.
- `python ci/sa_report.py --update-baseline` записывает текущие находки (обоснования совпавших
  записей сохраняются, у новых `reason` пустой — его заполняет человек; записи без обоснования
  отчёт перечисляет в замечаниях). Каждое обоснование дублируется в
  [STATIC_ANALYSIS.md](STATIC_ANALYSIS.md), как для iec_checker.
- Политика `--fail-on new` (по умолчанию) валит задание только на новых находках, `any` — на любых,
  `never` — только отчёт.

## Ограничения и риски

- **Внутренний API.** Имена сборки, типов и ключей взяты из CODESYS 3.5.17.30 (плагин 3.5.17.20) и
  не документированы. На другой версии `sa_check.py` либо найдёт их, либо завершится с кодом 3 —
  тогда правила включаются вручную в IDE ([MANUAL_STEPS.md, раздел 16](MANUAL_STEPS.md#16-static-analysis-light-правила-в-ide)),
  а находки берутся из генерации кода в IDE (окно «Сообщения» → копия в [BUILD_ERRORS.md](BUILD_ERRORS.md)).
- **Генерация кода** нужна устройству: проверено с CODESYS Control Win V3 (`4096 / 0000 0001`);
  с таргет-файлом ОВЕН ПЛК210 — не проверялось.
- **`cds.py build` и генерация кода.** `cds.py build` вызывает `app.rebuild()`: предупреждения,
  которые появляются только при генерации кода (например, `C0373 Адрес %QX0.0 не задан ни в одном
  устройстве`), в `build/build.json` не попадают — они есть в `build/sa.json`.
- **Полная версия Static Analysis** (лицензия) пишет находки в другую категорию («Сообщения
  статического анализа») с теми же кодами `SAxxxx`; `sa_report.py` разберёт их как находки
  неизвестных Light правил. Не проверялось: лицензии нет.
- **Ошибки компиляции.** В 3.5.17.30 правила Light выполнились и при ошибке `C0032` при генерации
  кода (`sa_compile_error.json`), но такой анализ отчёт считает неполным.
